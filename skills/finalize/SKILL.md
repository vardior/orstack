# Finalize

Execute the following steps in sequence on the current branch. **First, write the five steps into the task plan as five visible items — all five present before Step 1 starts.** Tracking them in prose does not count. A step you skip stays there with `skip: <reason>`; silent skipping is the failure this skill exists to prevent. The final message lists all five steps with their status (done, or `skip: <reason>`). Each step must complete before the next. Do not pause for approval between steps — only stop if genuinely blocked.

**Branch handling first:** if currently on `main`/`master` with uncommitted changes, create a feature branch named `or/<short-kebab-case-summary-of-the-fix>` (e.g. `or/fix-shared-snapshot-system-prompt-crash`) — a descriptive slug of the actual change. Do not ask for the branch name; pick one and proceed. Then identify the changed files (`git diff <base> --name-only` plus `git status`).

## Step 1: Verify Live

Exercise the changed flow for real — the repo's verification skill (`verify-<app>`, or whatever the repo's agent docs name) **when the change falls inside that skill's stated scope**; a skill scoped to one surface (say, the UI path) does not cover a backend-config or test-only diff, so apply the tier ladder in `references/evidence.md` directly instead of forcing the diff through it. The step never scales down. The default surface is the **whole job the change serves, end to end** — the feature's real trigger through its real output (a background-job change means a triggered job and the output it produces, not the preview endpoint that predicts it). Stopping lower needs a damn good excuse, written in `## For the PR` and in your final report: an irreversible customer-visible side effect, infrastructure that does not exist, or a cost the caller has not authorized. "The unit tests cover it", "it has no UI of its own", and "the seed data has no such case" are not excuses — build the data (the repo's snapshot or remote-env skill) or say you are blocked. The reviewer treats an unexcused lower tier as a finding. When the whole job is not reachable, `references/evidence.md` defines the lower tiers; read it before writing the evidence bundle, whose format it also defines. Builds and unit tests are not this step. Fix failures and re-verify before anything else. If verification ran in another agent, obtain its bundle path — do not re-describe its work from memory.

When the verification skill records outcomes, record one on the bundle the PR cites before Step 2: `caught` with a one-line note when a drive exposed a defect in the change or a regression, even one you then fixed; `blocked` with the cause when the harness or environment kept you from a product verdict; otherwise `confirmed`. These outcomes are how you measure whether the skill pays off, so an unrecorded verification counts as nothing.

When the diff changes anything a user sees, read `references/visual-checks.md` before driving the browser and walk the change as it says.

**Affected CI checks.** Live verification does not replace the checks CI runs. Against the PR's actual base, with staged, unstaged and untracked edits included: build every project that depends on a changed project, not only the edited one; run the existing tests that name a changed type, member, option, or a value whose acceptance changed; and run the repository's documented pre-push checks for the file types touched. Use the repository's CI recipe when one exists (named in the repo's agent docs or your global instructions) and its scope filters rather than a full-solution build by default. Record each command and result, and each check left unrun with the reason, in the evidence bundle; after Steps 2–3 change code, rerun only what those changes affect. Diagnose a red check before changing anything: update a snapshot or assertion only when the contract intentionally changed, and report a failure in shared CI infrastructure instead of patching around it.

## Step 2: Deslop

Run the `deslop` skill over the branch diff yourself, in one pass. It covers both slop (added comments, abnormal defensive code, `any`-casts) and structure (duplication, needless indirection, dead code, deep nesting). Spawn no separate simplifier agent; Step 3's review is the independent second look. Commit any resulting changes on top before review — never amend once Step 1 has recorded a `Head SHA:`, because that SHA must stay an ancestor of HEAD.

## Step 3: Code Review

Commit, then run the orstack `review` skill against that committed SHA, supplying the base and the evidence bundle from Step 1. When the repository ships a local mirror of its CI PR reviewer, run that on the local branch as the review instead, to approximate CI's review; its rules skip comments and test coverage, so then apply only `review`'s added-comment rule (step 3) and its verification and affected-CI evidence checks (step 4) to the same diff, and merge the results into one list. A rules-file fix it proposes goes to Or as a proposal, never into this change. It reviews the change in context against repository rules, reports actionable findings, and assesses whether verification covers the delivered change. A contested or expensive-to-undo diff earns one additional adversarial reviewer (or-mode's adversarial-review trigger). Address material findings and re-verify affected behavior before proceeding. If the reviewer returns no output, retry or perform the review yourself; empty output is never a clean pass. Merge decisions remain governed by the user's authorization and repository rules.

## Step 4: Clean the Diff

Drop strays before opening the PR: eval artifacts, `*.jsonl`/CSV outputs, scratch files, scaffolding tests, measurement harnesses committed as tests (profiler, `explain`, or large-seed tests that assert a database's plan rather than our code), leftover debug code, unrelated refactors. Instruction files — any `AGENTS.md`, `CLAUDE.md`, skill, or hook — are out of scope unless the task *is* about them, even when a repo rule invites "keep agent docs current": the option name and the class are the documentation, and an agent rewriting shared instruction files inside a feature PR is the alarming part. A worker's suggestion of such a note is surfaced to Or as a proposal, not applied. The PR contains only changes serving its stated purpose.

Then run `git diff --stat origin/<base>...HEAD`. When the diff spans more than one unrelated area (a top-level `src/<Project>` or service directory) or exceeds about 400 changed non-test lines, split it into one PR per area before opening. A schema or index change goes in its own PR. When the diff cannot be split, say why in one line of the PR body.

## Step 5: PR and Tail

No session owns its own tail: every session that opens or pushes a PR, in any repo, registers it with `pr-owner` before it ends, including a PR Or may merge himself. The owner is the dispatching lead (`lead:<lead session id>`) for a lead-dispatched worker, and `or` for Or's interactive session, whose events reach chief-of-staff's inbox. Do not also turn on the desktop app's Autofix or CI monitoring for that PR: each of its events wakes the whole session, most end with nothing to fix, and pr-owner already reports every state change.

Use the `visual-pr` skill to compose the description from the reviewed diff and Step 1's evidence bundle. It keeps the ticket first line, uses a structural sketch only when useful, and lifts `## For the PR` into `## Verification` verbatim. Keep local bundle metadata out of the body; the bundle path goes in your final report. Upload Step 1's required screenshots and recordings with `gh pr create --attach` or `gh pr edit --attach`; local file paths alone do not deliver media to reviewers. Replace superseded evidence attachments after fixes, and state any capture or upload blocker in `## Verification` and the final report. Push and open a regular PR, never a draft (the `pr` workflow if available, else `gh`), using the composed body, and read it back to confirm the description and attachments. Or's personal repos, anywhere Or is the only reviewer, take a direct commit to `main` after Steps 1–4 instead of a PR: there is nobody external to review it, so the tail is the push (and the repo's release script where one exists). For that path, link required media from the evidence bundle in the final report. Immediately after `gh pr create`, run `python3 <finalize>/scripts/pr-owner.py register --repo <owner/repo> --pr <pr> --head <sha> --owner <owner> --worktree <path> --branch <branch> --brief <path> --evidence <path> --resume <handle>`. Use `codex:<session id>` for a Codex worker or `claude:<session id>` for a Claude worker when known; omit `--resume` when unknown. After each later fix push, run `python3 <finalize>/scripts/pr-owner.py rearm --repo <owner/repo> --pr <pr> --head <new sha>`; in a repository whose Claude PR Review does not run on synchronize, a push that dismisses an approval re-adds `claude-review` itself, and a hand relabel on top races it: run `python3 <finalize>/scripts/claude-review-round.py <pr> --grace-sec 120 --started`, and only when it prints `not_reviewed` remove `claude-review` if present and add it again. Report `handed-off: pr-owner <owner/repo>#<pr>` and exit. Required checks and the review gate still define readiness; silence is not status. When the repository's CI recipe has a red-check triage section, follow it before reading the log. Never end with uncommitted work on the branch. When the PR merges while you still own the tail, remove its worktree before ending: from another checkout of the repo, plain `git worktree remove <path>` (never `--force`) and delete the local branch; a refusal means uncommitted work, so report it instead. Worktrees left behind pile up to hundreds of GB; the weekly local gc catches the rest.


**Claude review rounds.** In a repository using `claude-review`, read `references/claude-review-rounds.md` before the first round and run every round as it says.

## Important

- Stop and ask for guidance only if a step fails in a way you cannot fix
- The code review may surface issues that need fixing before PR creation
- Commit any changes from deslop before the PR step

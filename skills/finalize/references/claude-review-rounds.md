# Claude review rounds

Handle Claude's review one whole round at a time: a round is the Claude PR Review run on one head SHA. For a lead-dispatched worker, hand off the tail as finalize Step 5 says; the lead handles events as or-mode says. For an interactive session owning its own tail, run `python3 <finalize>/scripts/claude-review-round.py <pr>` as the round's background watcher. It exits once that head's run has completed and prints URLs and abbreviated first lines for findings Claude posted on that head, or `not_reviewed` when no run targets it; read each full finding before triage; pass `--await-run` right after re-arming so it waits for the new run to appear. In a Claude Code cloud session the script prints `cloud_session` and exits: subscribe to the PR, and the review run and its comments arrive as events. A run that did not conclude `success` is not a clean round: re-run it once with `gh run rerun`, then report it. Edit nothing for review while the run is in progress: findings land over several minutes, and fixing the first ones splits one round across several commits and re-reviews.

Sort the whole round into two buckets before touching code. **Worth a commit:** you can name the input or state that reaches this PR's changed lines in production and the wrong result it produces there: wrong behavior, data loss, a crash, a security hole, or a cost blow-up. **Nit:** everything else, whatever the reviewer titled it ("Bug:" included): simplification, efficiency with no measured cost, naming, style, "fragile" or "consider", a guard for a state nothing produces, interface symmetry, test-coverage wishes, hypotheticals, repeats of a finding already answered, and anything outside the PR's purpose, which also gets a ticket when worth keeping. Reply to each nit with its one-line reason and resolve it; never add code or a test only to quiet a reviewer. When a real defect lands on code an earlier review fix of yours added, stop patching: the previous fix was the wrong shape, so rework that part from the design or report it to whoever owns the PR. Stop the same way when a round's worth-a-commit findings are new cases of a class an earlier round already fixed, the same missing data or rule surfacing on another read: name that root cause to the PR's owner, with narrowing or pushing back as options, before pushing again.

Fix every worth-a-commit finding of the round together, re-verify the affected behavior, push once, and reply to each with the fixing SHA. A round with nothing worth a commit ends review: no push, no re-arm. After the push, follow finalize Step 5 for a dispatched worker. For an interactive owner using the round watcher, run the script with `--grace-sec 120 --started` first: a push that dismissed an approval re-adds the label itself, and a second label event cancels a run or doubles the review. Only on `not_reviewed`, remove `claude-review` if present, then add it with `gh pr edit --add-label claude-review` to generate a fresh label event. Never re-arm a head that already has a completed or active run; the script tells you which. Preserve unrelated labels, but never restore a prior head's approval/verdict labels. Own the new round through the script with `--await-run`; a push or a stale approval alone does not complete the tail. Re-arm at most twice per PR; under pr-owner that is the registration budget in or-mode. After that, hand the open findings to the PR's owner with your judgment of each instead of pushing again.

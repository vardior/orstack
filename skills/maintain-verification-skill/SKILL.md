# Maintain a verification skill

A feature map rots the moment the app changes. This skill is the upkeep loop for a skill generated by `create-verification-skill` (or any project-local verification skill with a feature map). The unit of rigor is the feature, not every sentence: cover every feature file from source and exercise every feature live, without terminalising every bullet.

## Outcomes

Pick one, and say which:

- **clean** — every feature got source and live coverage; nothing worth shipping. No branch, no shipment.
- **changed** — one shipment of proven doc, harness, or map corrections, to the skill's own ship target (see step 6).
- **blocked** — coverage could not finish or a proven fix could not ship safely. Say exactly what blocked it.

## Scoped run

`--features <slug,...>` limits the pass to those feature files, typically the ones agents' Harness lines named or whose cited source changed recently. Run every step for the named features only: their index rows, one source read per feature, a live drive of each, triage, and one shipment. The outcome describes the scope, so `clean` means those features are covered, not the whole map. A full pass, or a stamp refresh across features nobody named, needs Or's explicit audit request. Upkeep drives record no verification outcome: outcomes measure product verification only.

## Edit scope

Only edit the verification skill's own directory (its SKILL.md, features/, and any harness scripts it owns). Never edit product code during a run: a behavior the map describes that the app no longer does is either doc drift (fix the map) or a product regression (report it, don't paper over it in docs).

## Pass

0. **Locate the target.** Find the verification skill to maintain: the project-local skill whose body has launch/drive sections and a feature map (usually `.agents/skills/verify-*/` or `.claude/skills/verify-*/`). Resolve symlinks and deduplicate the same skill exposed to both runtimes. Several distinct candidates → ask which one; none → stop and point at `create-verification-skill` instead of inventing a target.

1. **Index hygiene.** Read the feature map README and glob its sibling files. Fix missing, extra, duplicate, or dead entries. Lightweight; no generated inventory. The index only routes: each entry is a phrase of about 10 words naming the surface and its main behaviours. What a feature proves belongs in its own file's opening paragraph, so an entry that grows into a description moves there. Each feature file's `Source` section lists the repository-relative paths that implement it; add or correct it whenever a run reads the feature's code, since routing a diff to features and the drift signal both depend on it.

2. **Source wave.** Batch feature files across at most four read-only subagents; never launch one agent per feature across a large map. Use cheaper models for mechanical sweeps; when using Sol for source analysis, select medium reasoning. Each feature still gets its own explanation of "how does this user-facing feature work?" from source, likely doc drift with citations, and one concise live-verification recipe. Source reviewers stay read-only. Children explicitly assigned setup or verification may build and launch services with named ownership, isolated ports where needed, and a cleanup obligation. Coordinate builds and service lifecycles so children do not build the same checkout concurrently or launch competing copies of a shared stack; the coordinator owns the live-pass sequence. Return shape per feature: feature summary / source entry points / likely drift or none / one recipe.

3. **Reconcile.** Every feature file has a returned summary. Merge overlapping recipes into as few app states as practical. Spot-check cited drift; don't re-prove clean claims. Sweep recent churn for user-facing surfaces missing from the map — require a concrete source path before calling one missing. A changed path you cite in a feature this run puts that feature in scope: drive it in the live pass, even under `--features`, because the next scoped run starts after that change and won't name it.

4. **Live pass.** Required even when source looks clean. The coordinator owns all driving; follow the verification skill's own launch model — one long-lived instance driven serially for servers and UIs, or a fresh isolated session per drive for short-lived CLIs (the skill's Launch section decides, not this one). Exercise every feature at least once, and hold three invariants the whole pass, whatever the failure: (1) never drive an instance you haven't health-checked since it last did something surprising — doctor before first drive, doctor on each fresh session where sessions are the unit, doctor again after any failed drive, and where doctor can't see the failure (a wedged UI state on a healthy process), reset to a known state or relaunch rather than hoping; (2) evidence captured so far survives every cleanup, checked at its named location, not assumed; (3) nothing a drive started outlives that drive's usefulness — failed-iteration residue is cleaned whether the session is stuck, exited, or shared (for a shared instance, clean the residue, not the instance). A doctor failure caused by skill drift is drift: fix it under edit scope and retry once — restart whatever the fix invalidated, nothing more — before calling the pass `blocked`. A feature that can't be reached is `verified-unreachable` only with the concrete prerequisite (auth, entitlement, OS, external state) and the route attempted; if the map omits that prerequisite, that's drift. Any harness fix from triage gets re-driven live before it ships. Final teardown happens after the last drive of the run — including those re-proofs — so nothing outlives the run (evidence stays, per the skill).

5. **Triage.** Wrong or missing user-POV description → doc drift, fix it. Working behavior the harness can't drive → harness gap, fix it; a harness fix follows the same helpers rule as generation (scripts executable, invocation documented in the skill body). A procedure agents run by hand — a multi-step recipe in the docs, or a script copied from one evidence bundle to the next — → move it into the skill's control CLI as a subcommand and replace the prose with that one command. App behavior that's actually broken → product gap; record it for the user, keep it out of this PR.

6. **Ship or stop.** Resolve the ship target before writing anything: a verification skill checked into the project ships as one PR to that project, while one that deliberately lives outside the project tree — its own repository, symlinked into the project, or otherwise excluded from the project's version control — ships as a commit to the repository that actually owns the skill directory, and opening a project PR for it is wrong. Make that commit in a worktree of the owning repository (`~/wt/<repo>/<slug>` from a freshly fetched `origin/main`), fast-forward its main and push. Its main checkout is the copy agents load, so it is never edited directly. `git -C <skill-dir> rev-parse --show-toplevel` answers this; the generated skill should also say so in its own body, and its answer wins over the directory layout. For changed: one shipment of proven corrections to that target, re-read every changed file first. For clean or blocked: no shipment, report the outcome and the coverage honestly.

Keep concise run notes (features covered, unreachable prerequisites, confirmed drift, outcome) in a scratch location; don't commit them.

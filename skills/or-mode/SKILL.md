# or-mode

> **Work in progress, still changing.** If a step fights the task, produces ceremony without
> catching anything, or is missing a case you just hit: adapt it in place and name it under
> `Harness` in your final report. Silent workarounds are lost signal.

The conductor for nontrivial work. It adds no new capability; it binds task type → discipline → the skills that already exist, and makes skipped steps visible instead of silent.

Authority and PR rules live in `~/.claude/CLAUDE.md` and `~/.agents/AGENTS.md`; model routing and delegate dispatch live in the `delegate` skill. The active runtime's global file overrides anything in this skill or its playbooks on conflict. Repo-local CLAUDE.md/AGENTS.md override both for repo facts (base branch, test commands, commit conventions, delivery mode). Precedence: explicit task instruction > repo contract > active global rules > this mode's defaults. A launch brief from whoever started you is the explicit task instruction: its scope, how to reach your launcher, and where your report goes win over this mode's defaults.

## Non-negotiables

**Start every multi-step task by matching it to a playbook and copying that playbook's steps into the runtime's task plan verbatim, before any task-specific items.** The failure mode is reading a playbook and then writing a bespoke plan that drops its named steps. A step you choose not to do stays in the plan with a one-line `skip: <reason>`; skipping silently is not allowed.

Standing triggers, independent of playbook:

- **Work that will change code or open a PR runs in its own worktree.** Launched in one? Stay in it. Otherwise create one off the fresh base branch: `git -C ~/<repo> worktree add ~/wt/<repo>/<slug> -b or/<slug> origin/<base>`. Delegate briefs go in its `briefs/`, the decision trail in its `decisions.md`; both stay out of git through the repo's `$(git rev-parse --git-common-dir)/info/exclude`, so add them there when missing. A read-only Investigation needs no worktree.
- **Empirical fork → prototype, don't ask.** Before asking the user a "which approach / how should I / what should this do" question, classify it. If the answer is observable by running something (behavior, timing, layout, output, perf), it is not the human's to answer — sketch it via the Prototype playbook and let the result decide. Reserve questions for genuine product or preference calls no experiment can settle, and for the authority gates in the active global instructions.
- **Task arrives as a thread, ticket, report, or someone else's diagnosis → restate it first.** Before any plan: the problem in plain words (what is broken or wanted, for whom), the observable that says it is solved, and which parts of the input are the reporter's *hypothesis* rather than the symptom. Show the restatement to the requester (Or, or the thread that launched you) when the ask was ambiguous or arrived through a noisy channel; a fixation on a red herring is corrected in one line here and in a day after code. Then work from the restatement, not the thread.
- **Any code → name the data shape first**, and choose its organizing structure before writing logic: a state machine over scattered booleans, a table/registry over spread-out branching, a typed model over repeated shape assumptions.
- **Repeated corrections in one area → `/agent-ready` or `$agent-ready`.** Use SWEEP for an existing surface and WIP for a feature being built; assign each correction a layer before adding prose.
- **A seam that is expensive to undo → `design-it-twice`** before implementing: a published interface, a persisted data shape, a cross-service contract. A module boundary alone is not the trigger — name the data shape (previous trigger) and proceed. Do not fold an expensive-to-undo decision silently into implementation; skipping when it does apply stays as `design-it-twice skipped: <reason>`.
- **One rule across many reads → read-surface table before code.** Scoping, authorization, tenancy, or a flag that must hold on every read of a feature: list each read with the stored field that answers it under the rule and the repository file that already does it that way. A read no stored field answers is a `can't` row; a pattern with no precedent file is non-standard, never called standard. Show Or the table before any worker starts. When a `can't` row breaks a condition he set, recommend push-back or a narrower slice; never carry it into the build as an accepted exception.
- **Contested design or high-stakes diff → adversarial review** = finalize's routine `review` pass plus **one** adversarial reviewer briefed to refute the diff (cross-family: a `codex-worker` when the author was Claude), routed through `delegate`. That is the fan-out cap's sanctioned second. Never `code-review medium`/`high` for this: both run the same eight finder angles plus a verifier per candidate — a fleet by construction, whatever the call looks like. Reviews pin to a committed SHA — commit (even `wip:`) before dispatching reviewers, pass that SHA in every review brief, and dispatch no fix round until every reviewer of that SHA has reported. A review of a mutable tree scores a moving target.
- **A review finding that changes product semantics is not a correctness finding.** Billing, pricing, quotas, user-visible behavior contracts: park it as a ticket plus a decision-trail line and keep working everything else — never implement it while the human is unavailable. Reviewer consensus is not product authority.
- **Live verification → the repo's `verify-<app>` skill** when one exists (generate one with `create-verification-skill` when a repo you keep returning to has none). No verify skill → drive the real surface directly (browser for web, PTY/tmux for CLIs, simulator for iOS, curl for services). "It compiles" and unit tests are not live proof.
- **Any autonomous or fan-out run keeps a decision trail** — the trigger is the work's shape (delegates in flight, multi-round orchestration, the human quiet for a stretch), not an explicit "going to bed": one appended line per decision (timestamp, choice, why, evidence pointer) in the worktree's `decisions.md`. A run with no trail can't be audited or resumed.
- **One agent per question; a second only to disagree.** A phase — design, investigation, review — runs with one agent. A second is added only when its value is *disagreement* rather than throughput: a different model family reading the same artifact independently, on a decision that is **expensive to undo** (a published interface, a persisted data shape, a cross-service contract, a migration, a deploy). Three agents at one question is never the answer — when one pass was not enough, the fix is a second pass with a sharper brief, not more readers at once. This caps fan-out at a *single* question; it does not cap parallelism across *disjoint* units of work, where separable slices still get a worker each (Feature step 3). A fleet aimed at one problem is the expensive way to avoid scoping it.
- **Orchestrator hands stay clean.** When delegation is available, the main thread does not run build/test loops or mechanical edit sequences — any fully-specified execution goes to a delegate (codex by default). Main-thread shell use is for orientation and verdicts: `git status`/`diff`, a quick grep, spot-checking a worker's claimed evidence. Three consecutive mechanical edits or two builds in the main thread means you are doing a worker's job — stop and dispatch. Below that line, just do it: dispatching a worker for a two-line pinned edit costs more than the edit. Main-thread context is the coordinator's state; filling it with build output destroys it at compaction. For a lead-dispatched PR, the worker hands off and exits under finalize Step 5. The lead writes `lead:<its session id>` as the owner in the brief and keeps one background `python3 <finalize>/scripts/pr-owner.py wait --owner lead:<id>` at a time; when it returns, read the event JSON, act, run `python3 <finalize>/scripts/pr-owner.py ack <event id>`, and start the waiter again; unacked events replay. The launchd job `com.orstack.pr-owner` sweeps every 120 seconds, so no model turn polls GitHub. RED: use the repository's CI failure-triage procedure to distinguish the diff’s own failure from infra; rerun infra or resume the same worker for its own red. FINDINGS: resume the worker to fix or answer. CONFLICT: resume it to merge the base. NOT_REVIEWED: refresh the `claude-review` label and rearm. READY: apply the repository’s existing merge policy. MERGED or CLOSED: release the registration and clean up the worktree. HEAD_MOVED, TIMEOUT or WATCH_ERROR: the lead investigates. For a whole new review round, a compacted worker, or an unusable resume handle, brief a fresh worker from the registration record instead. A registration has a two-rearm budget; beyond it, stop, report the shared root cause to Or, and register again only with `--or-approved "<his words>"`.
- **Design still under review → answer in chat only.** While Or is reviewing or asking design questions, do not republish plan or status pages or edit tickets after each turn; update them once, when he calls the design settled or asks for the update. Each mid-discussion rewrite is overwritten by the next correction.
- **Skill or tooling broken mid-task → fix it in its own PR/commit.** Don't block on it, don't silently work around it.
- **Text other people read is written for a teammate who has never heard of our tooling.** That covers Jira tickets, PR bodies, review replies and Slack. Give the product behavior, a repro in product terms (users, roles, screens, API calls) and code locations. Leave out orstack, verify skills and their CLIs, workers, evidence bundles and local paths; evidence that exists only on this machine is "available from Or on request".

## Subagents

You own every subagent's work: review the diff and write your own summary; never pass through what it said. Delegate only when the user or the active runtime's instructions allow it, and route every delegate through the `delegate` skill — one model decision per agent, never a fleet default. Prefer fresh subagents with consolidated scope over interrupt-chained resumes: resumes are for small fixups only; a full review-round fix goes to a fresh delegate with a consolidated brief. A resumed worker that compacts silently drops directives, so REPORT must disclose any compaction. Route bulk reads (long transcripts, big logs, full reports, evidence bundles) to subagents and keep summaries in the main thread. A worker's report reaches the main thread as its verdict plus evidence paths; open at most one artifact per claim you need to check, such as one screenshot or one log excerpt, never the whole bundle. The same holds for a worker's diff or a review round: the main thread reads `git diff --stat` and the verdict of a `review` run in a subagent, and opens only the hunks a finding cites, never whole files or the full diff. Dispatch is sized by the fan-out cap above: agents are added for *disjoint work*, never for coverage of one question. The hands-stay-clean trigger applies here with no exception for "it's faster to just do it": a fully pinned revert/fix spec is the *most* delegable work there is, not a reason to execute inline.

**Every delegate — same-runtime subagent or codex worker — gets the same brief template: copy `brief-template.md` (next to this file) and fill all eight fields.** A dispatch missing any of the eight headers is malformed — do not send it; a field you cannot fill is a unit you have not scoped yet. Briefs live on disk in the worktree (`briefs/<name>.md`), and every re-dispatch or fix-round brief is written from that file — never from a compaction summary, which drops the discriminating condition ("thinking **off**" became "one chat turn"). Briefs on disk made two silent compactions and a triple agent kill cost nothing. No delegate inherits this skill or the `delegate` skill, and the global instruction files are thin pointers rather than a rule set — a same-runtime subagent picks up `~/.claude/CLAUDE.md`, a codex worker only `~/.agents/AGENTS.md` and the repo's AGENTS.md. There is no ambient safety net: the brief is load-bearing, so inline every rule the task depends on.

A Codex worker follows `codex-exec.md` in this skill's directory (brief it with the absolute path) for reads, long jobs and questions; every Codex brief names it.

## Final report

Code work ends with one report, sent where your launch brief says (a parent's handoff folder, a thread) or, with no brief, as your reply. A report never goes to Or as a needs-user item, which takes only questions and manual steps for him. Lead with the outcome, link every PR and ticket, and use these headings, writing `none` under an empty one:

- `Built`: what changed and what it does for its user.
- `PRs`: each PR with its state; `provisional — tail pending` while CI or review bots are still reporting.
- `Evidence`: the evidence bundle path and its one-line verdict.
- `Needs you`: only decisions a person must make, each one question with its options and your recommendation. A finished PR that is ready to merge, or a check also red on the base, is a fact for Loose ends, not a decision. A lead asks Or each worker's `Needs you` item as one `needs_user` question with its context, short options and `recommended` set; an item with no recommendation goes back to the worker.
- `Loose ends`: facts the reader should know but need not decide, and work you ticketed instead of doing.
- `Harness`: where the stack's guidance (this skill, a playbook, a verify recipe, the repo's agent docs) disagreed with reality or was missing, as `<where> | said: <what it said> | true: <what was true> | cost: <minutes or attempts>`. Report only what an agent would hit again, could not find in the code or docs within a minute, and lost real time to; never your own mistakes or a rule you dislike. Carry your delegates' Harness lines up into yours, and act on them before closing the task: a line naming a verification recipe becomes a fix shipped to that skill's ship target (the repo that owns the skill) through a worker or a `maintain-verification-skill` run; a line naming an orstack file becomes an orstack fix. Reporting a line is not fixing it.

## Replies

Or's concise output style governs. Additions from this mode: frame impact for the consumer and the maintainer (who notices this change, and what does the next owner of the code inherit) before implementation detail; never fabricate a link, citation, or transcript reference; paste verification output verbatim when it is the proof. Comments in produced code follow the active repository and global instruction files — including in delegates' diffs and verify scripts.

Proactively suggest a reply only when the original conversation is still unanswered by Or and a useful answer requires substantive investigation across sources or code. Check the full thread and recent conversation before starting, then recheck immediately before delivery. Routine answers, acknowledgements and requests for missing context stay quiet: no draft, reply-choice item, reminder or delegated task. Do not turn those into a clarification offer. An explicit request from Or to draft or send a reply remains an authorized task. (Or, 2026-11-05.)

## Playbooks

Match the task, open the file, copy the steps verbatim. Work no playbook fits gets a bespoke plan that still honors the standing triggers above.

- **Investigation** — read-only question: how does X work, why was Y built this way, are we sure. `playbooks/investigation.md`
- **Bug fix** — reproduce, root-cause, fix with runtime evidence. `playbooks/bug-fix.md`
- **Feature** — new or changed behavior, built from a named data shape. `playbooks/feature.md`
- **Refactoring** — behavior-preserving change to structure. `playbooks/refactoring.md`
- **Prototype** — throwaway sketch to settle a design or empirical fork cheaply. `playbooks/prototype.md`
- **Babysit** — drive a PR to merge-ready: conflicts, review threads, CI. `playbooks/babysit.md`
- **Autonomous run** — a long task driven to a predicate without stopping. `playbooks/autonomous-run.md`
- **Session pickup** — resume or take over prior in-flight work. `playbooks/session-pickup.md`
- **Pause safely** — suspend in-flight work so a cold start can resume it. `playbooks/pause-safely.md`
- **Opening a PR** — invoked at the end of every code playbook. `playbooks/opening-a-pr.md`
